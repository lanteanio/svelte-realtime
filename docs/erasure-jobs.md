# Erasure jobs

A failed or interrupted erasure must not be forgotten, so `configureForget({ jobs: true })` (in-memory; passing it again keeps the configured store) or `configureForget({ jobs: store })` (a `ForgetJobStore` that survives restarts) records every `live.forget` as a job. The job is recorded before any surface is touched - if that write fails the call rejects with `FORGET_JOB_FAILED` and erases nothing - and the outcome afterwards. With a job store configured, `tenantId` is required.

Every call is its own job under a random UUID, so the reference reveals nothing about the user. The reference is `res.job` on success, the non-enumerable `job` property of a rejection (never part of `details`, so an error rethrown to a client does not carry it), and the `job` attribute of `forget.incomplete`.

## Shared steps and in-memory steps

An erasure has two kinds of steps.

- **Shared steps** - the durable store (`configureForget({ store })`) and a dead-letter store other than the built-in one. Their data is shared, so any process can finish them. The job store tracks these, and a job's status describes them: `completed` means every shared step is done.
- **In-memory steps** - push, presence, rate limits, idempotency, smooth state, live aggregates, named CRDT documents and the built-in in-memory dead-letter store. Their data lives in one process, so only that process can erase it. The job store does not track them.

In-memory erasure is per process. When a job store is configured, the process that ran `live.forget` keeps the in-memory steps that failed, with what it needs to run them, and retries them by itself - after a delay that doubles from one second to an hour - whatever the store says about the job, and goes on doing so after the job store is cleared. Without a job store a failed in-memory step is only reported; call `live.forget` again. Progress is kept per holder where a step reaches other users' data: each aggregate (each window of one) and each document of each declaration. The first run records which holders exist (aggregates by output topic, documents by declaration and name); a retry runs only those of them that failed. It never runs one that succeeded, so an aggregate reset or a document dropped earlier, which holds other users' data by now, is left alone, and never one that appeared since (an aggregate registered or renamed after a reload, a declaration whose authority loaded later), which holds only data written after the erasure. A failed holder that has since gone away is set aside like one that can never succeed. A holder that can never succeed as configured - an aggregate without an erasure policy, a document declaration without `drop` - is reported once and set aside (`blocked`) without touching the others; the job's in-memory work is exhausted at once when nothing else is left. The other in-memory steps erase only the user's own entries and are safe to repeat. `listForgetJobs()` on that process shows the owed steps in each job's `local` field. A job the store has no record of is listed with `status: null` ahead of the store's rows, in the order this process recorded it, within the listing's `limit`; its times come from the process clock and the store's rows from the store clock, so the two are not sorted together. A process that exits takes its memory with it, and with it both the data and the steps it still owed.

In a cluster, each worker holds its own in-memory state, so `live.forget` must run on every worker. Publish the erasure request with an unscoped `platform.publish` on a topic no client may subscribe to (deny it in your guard), and call `live.forget` from a static `live.effect` on that topic without `debounce` (a debounced effect keeps only the last event). A tenant-scoped publish such as `ctx.publish` from a tenant connection lands on the tenant's wire topic and never fires a static effect. Effects reach other workers only through the cluster bus from `svelte-adapter-uws-extensions` (`realtime({ bus })`): the adapter's built-in cross-worker relay delivers frames to sockets, not to server-side watchers, so without the bus the effect fires on the publishing worker only. The bus delivers at most once: a worker that is partitioned or restarting misses the request and nothing signals it, so re-issue erasure requests periodically, or reconcile from your own records, until every worker has run them. Each worker's call is its own job; the shared steps run once per job.

## Listing and resuming

`listForgetJobs({ status, limit })` lists jobs with their status (`pending`, `failed`, `exhausted`, `completed`, `abandoned`), attempt count, timestamps, `retryAt`, total rows removed, last failure code and surfaces, and the in-memory steps this process still owes (`local`). An open job holds the raw user id; a finished one does not.

`resumeForgetJobs({ id, limit, exhausted, onForget })` runs open work again: first the in-memory steps this process owes whose retry time has come (results with `steps: 'local'`), then the jobs whose shared steps are due (`steps: 'shared'`) - failed ones past `retryAt`, with a delay that doubles per attempt from one second up to an hour, and pending ones whose run let its lease expire - earliest due first. With `id` it runs that job whatever its retry time. Run it at startup and on a schedule, or let `configureForget({ resumeIntervalMs })` run it on an interval. A run first claims the job, so a job another live run holds reports `skipped`, and two runs never work on one job together. The stored `cascade` is replayed only in a shape `live.forget` accepts; a damaged record fails with `INVALID_REQUEST` and stays listed as a failed job.

A run holds its job under a lease of one minute, renewed every 20 seconds for as long as it goes on, with one renewal in flight at a time; the lease only runs out when the process dies or its renewals stall. A run still going after 15 minutes is reported as `forget.run-overdue`, and again every 15 minutes, by the monotonic clock; it keeps its job, so no second run starts on it. If the run is stuck, abandon the job: `abandonForgetJob(id)` asks the store to cancel the run, and on the process running it also cancels the run at once; elsewhere the run's next renewal answers that it was cancelled. The cancelled run starts no further step, its pending store calls are abandoned (the durable store's `purgeUser` receives an `AbortSignal` it may honor), it rejects with `FORGET_CANCELLED`, and the job ends abandoned. A run that already finished every step completes instead, whichever process abandoned it. This holds for a stalled run whose lease ran out too, as long as no other run claimed the job: the lease is still its own, so it learns of the cancellation at its next renewal or outcome write. The job's user id, audit hash and cascade are deleted as soon as the cancellation is recorded, whether or not the run is still alive. A job whose run died stays listed as `pending`, with nothing user-derived, until the next `resumeForgetJobs` on any process marks it abandoned. Should that happen while the run is only stalled, the run is still told it was cancelled when it wakes, and ends with `FORGET_CANCELLED` even if it had finished every step.

A run that stalls past its lease can find its job taken over: another process claimed it and runs it now. The stalled run's next renewal answers that it no longer holds the lease, and the run just stops: it starts no further shared step, the same `AbortSignal` fires, it records no outcome and abandons nothing, and it rejects with `FORGET_INCOMPLETE`, unless its shared steps had already finished or failed before it learned of the loss, in which case it settles as they did (resolves, or rejects with `FORGET_STORE_FAILED`), still without recording an outcome. The run that holds the lease finishes the shared steps; the stalled run's in-memory steps still belong to its process, which keeps and retries the failed ones as usual. Only `abandonForgetJob` cancels a job.

## Jobs that cannot finish

A job whose shared steps fail on 24 runs stops running by itself: it becomes `exhausted`, stays listed with its last error, and `forget.job-exhausted` reports it. In-memory steps that fail on 24 tries likewise stop and are reported as `forget.local-exhausted`. Exhausted in-memory work is kept for a day, then dropped with `forget.local-dropped`; `configureForget(null)` drops it at once, while work still being retried goes on. Fix the cause, then run `resumeForgetJobs({ exhausted: true })` to resume every exhausted job and this process's exhausted in-memory steps (blocked holders included), or `resumeForgetJobs({ id })` for one. To give a job up, call `abandonForgetJob(id)`: it drops the job's user id at once and the in-memory steps this process owes for it, and marks the job `abandoned`; a job whose lease a run holds is cancelled as described above and marked `abandoned` when that run stops or the next resume finds its lease expired. `configureForget(null)` drops exhausted in-memory work too, reported as `forget.local-dropped` with `reason: 'reset'`. A shared step whose store has since been removed from the configuration fails on every run until the store is configured again or the job is abandoned.

## Retention

An open job holds the raw user id, the cascade and the audit hash, because a resume needs them. A completed or abandoned job keeps nothing user-derived: its user id, cascade, step list and audit hash are deleted, leaving the reference, tenant, status, counts and timestamps. The audit trail belongs in your `onForget` hook, under your own retention. A durable store deletes completed and abandoned jobs after a retention window of its own; 30 days is a reasonable upper bound. Keep the window for abandoned jobs well above any run stall you expect: once the record of a job a cancellation abandoned is deleted, a stalled run that wakes is answered `false` by `renew` and reports `FORGET_INCOMPLETE` instead of `FORGET_CANCELLED`. Set `hashKey` whenever jobs are on: without it the audit hash of an open job is an unkeyed SHA-256 that anyone with the store can match against candidate user ids.

## Time bounds

Every store call a run waits on - the job record, each surface, the durable store and the outcome write - can be bounded with `configureForget({ timeoutMs })`, with or without a job store; without it (the default) an erasure waits as long as the store takes. A call that does not answer in time fails its surface, so a hung store cannot hold `live.forget` forever and does not keep the other surfaces from running. A durable purge that commits after its timeout still announces the owner changes it reports. The call itself keeps running in the store, so every surface must tolerate a late finish.

When the job record cannot be confirmed - `begin` rejects, perhaps after the store committed it and the reply was lost, or times out - the call rejects with `FORGET_JOB_FAILED` and erases nothing. The process then abandons the record should it exist or land later, trying when the call fails, when a late reply arrives and at its next resume, so a refused erasure does not run afterwards. Only if the process exits before that does the recorded job run later like any other, completing the erasure that was asked for.

## In-memory store

`createForgetJobStore({ max })` holds at most `max` jobs (default 10000) and times leases by the process clock. A new job makes room by dropping the oldest job that will not run by itself again: completed or abandoned first, then exhausted ones, each reported as `forget.job-evicted`. A pending or failed job is never dropped: while every held job is one, `live.forget` rejects with `FORGET_JOB_FAILED` before erasing anything, so no erasure goes unrecorded. Resume or abandon open jobs to make room. The store lives in one process and does not survive a restart. Each process separately keeps the in-memory steps it owes for at most 10000 jobs; past that it drops its oldest exhausted job to make room, and when none is exhausted it does not keep the new job's steps. Either way `forget.local-dropped` reports it; a job still being retried is never dropped.

## Store contract

A store that must survive restarts implements these methods, each atomic per job `id`; every method may return a promise. The shared steps themselves - the durable store's `purgeUser` and a shared dead-letter store's `purgeUser` - must tolerate concurrent calls for the same user, since every worker's job runs them, possibly at the same time. With a job store, the durable store's `purgeUser(tenantId, userId, cascade, { signal })` receives an `AbortSignal` that fires when the job is abandoned or the run loses its lease to another run; a store may stop early on it. Times come from the store's own clock - Redis `TIME`, PostgreSQL `now()` - never from the caller, so process clocks do not decide leases. A lease belongs to one run and lasts until the store-clock time `leaseMs` after it was granted or last renewed; the run keeps it, even past that time, until another run claims the job.

| Method | Contract |
| --- | --- |
| `begin({ id, runId, leaseMs, userIdHash, tenantId, userId, cascade, shared })` | Create a `pending` job with `attempts: 1` and `rowsAffected: 0`, open steps `shared`, and the lease of `runId` for `leaseMs`. Durable before it resolves. Reject when `id` exists. |
| `renew({ id, runId, leaseMs })` | When `runId` holds the lease and no cancellation was asked for, extend it to `leaseMs` from now and resolve `true`. When `runId` holds the lease and a cancellation was asked for, or the job was abandoned through a cancellation while `runId` held it (`cancelledRunId`), change nothing and resolve `'cancelled'`: the run stops and abandons the job (or completes it, had it finished every step and the job is still open). When `runId` does not hold the lease (another run claimed the job, or it is finished or unknown), change nothing and resolve `false`: the run stops its shared steps and records nothing. The two answers must stay distinct, since only the first ends the job. |
| `claim({ id, runId, leaseMs, exhausted })` | When the job is `pending` or `failed` - or `exhausted` and `exhausted` is true - and no unexpired lease holds it: give the lease to `runId` for `leaseMs`, set `pending`, increment `attempts`, set `updatedAt`, and resolve `{ userId, userIdHash, tenantId, cascade, attempts, shared }`. A job whose cancellation was asked for and that no unexpired lease holds is abandoned (as `abandon` does) and resolves `null`; it is never claimed. Otherwise resolve `null` and change nothing. A failed job is claimable before its `retryAt`. |
| `complete({ id, runId, rowsAffected })` | Only when `runId` holds the lease, whether or not a cancellation was asked for: set `completed`, `completedAt` and `updatedAt`, add `rowsAffected`, clear `error`, release the lease, delete `userId`, `userIdHash`, `cascade` and the step list, resolve `true`. When the job was abandoned through a cancellation while `runId` held it, change nothing and resolve `'cancelled'`. Otherwise resolve `false`. |
| `fail({ id, runId, code, failedSurfaces, sharedDone, rowsAffected, retryAfterMs, exhausted })` | Only when `runId` holds the lease: remove `sharedDone` from the open steps, add `rowsAffected`, set `error: { code, failedSurfaces }` and `updatedAt`, release the lease, keep `userId` and `cascade`, and set `failed` with `retryAt` `retryAfterMs` from now - or, with `exhausted`, `exhausted` (never due again, claimable on request). When a cancellation was asked for, abandon the job instead (as a sweep does, keeping `runId` as `cancelledRunId`) and resolve `'cancelled'`; resolve `'cancelled'` too when the job was already abandoned through a cancellation while `runId` held it. Otherwise resolve `true` after a recorded failure and `false` when `runId` does not hold the lease. |
| `abandon({ id, runId })` | When the job is pending, failed or exhausted and no run holds its lease (it was released, or `runId` holds it): set `abandoned`, release the lease, delete `userId`, `userIdHash`, `cascade` and the step list, resolve `true`. When another run holds the lease, expired or not - a run keeps an expired lease until another run claims the job: record a cancellation, delete `userId`, `userIdHash` and `cascade` at once (the run holds its own copy; status, lease and step list stay), and resolve `'cancelled'` - `renew` then answers `'cancelled'` to that run, which stops and abandons the job, while `complete` and `fail` still close it. A cancelled job no unexpired lease holds is abandoned by the next `claim` or `due`, instead of being claimed or returned. Every abandon through a cancellation (by `claim`, `due` or `fail`, or by the holder's own `abandon({ id, runId })` of a cancelled job) keeps the run id that held the lease as `cancelledRunId`, so that run is answered `'cancelled'` rather than `false` afterwards. Resolve `false` for an unknown or finished job. An abandoned job is never claimed. |
| `get({ id })` | The job as `list` shows it, or `null` when the store holds no record of it. |
| `list({ status, limit })` | Jobs oldest `createdAt` first, optionally one status, at most `limit`, without `userId`, `cascade` or the step list. |
| `due({ limit, exhausted })` | Pending jobs whose lease expired and failed jobs past `retryAt`, earliest due first, then `createdAt`; with `exhausted`, the exhausted jobs with no unexpired lease instead, oldest first. At most `limit`. Every cancelled job with no unexpired lease is abandoned, not returned, independent of `limit`, so none stays pending. |
| Retention | Delete completed and abandoned jobs after a retention window the store chooses. |

In PostgreSQL `user_id`, `user_id_hash` and `cascade` are nullable columns: a finished job drops them, and a cancellation nulls them on a row that is still pending. `claim` is one statement: `UPDATE forget_jobs SET lease_run_id = $runId, lease_until = now() + $leaseMs * interval '1 millisecond', status = 'pending', attempts = attempts + 1, updated_at = now() WHERE id = $id AND (status IN ('pending', 'failed') OR ($exhausted AND status = 'exhausted')) AND (lease_run_id IS NULL OR lease_until <= now()) RETURNING ...` - completed and abandoned jobs never match. The claim statement adds `AND NOT cancel_requested`, and `claim` and `due` first abandon cancelled jobs no unexpired lease holds (`cancel_requested AND (lease_run_id IS NULL OR lease_until <= now())`, which also catches a lease that `fail` released). `abandon` records `cancel_requested` and nulls `user_id`, `user_id_hash` and `cascade` when `lease_run_id IS NOT NULL AND lease_run_id IS DISTINCT FROM $runId`, and `fail` abandons the job instead when `cancel_requested` is set. Every abandon through a cancellation sets `cancelled_run_id = lease_run_id`; `renew`, `complete` and `fail` answer `'cancelled'` when `status = 'abandoned' AND cancelled_run_id = $runId`. `renew`, `complete` and `fail` add `AND lease_run_id = $runId`; `renew` reads `cancel_requested` in the same statement to answer `'cancelled'` instead of extending the lease. In Redis each method is one script that reads `TIME` and works on the job hash and a due sorted set; in Redis Cluster a script must only touch keys in one slot, so give the job hashes and the due set one hash tag (for example `forget:{jobs}:<id>` and `forget:{jobs}:due`).

An outcome a store does not record (it throws, times out, or answers `false` because the run no longer holds the lease) leaves the job open and emits `forget.job-unrecorded`; the job is due again once the run's lease expires.
