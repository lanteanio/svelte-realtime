## Consumer changes

### Added: public CRDT convergence checks

`runCrdtConvergence` drives concurrent Yjs documents through native document RPCs and checks their complete map, array and text state against an independent ledger under seeded ordered or duplicated delivery, while deliberate loss or corruption must fail, with actual execution counts and source provenance reported for every completed run.

- **Affects:** Maintainers and correctness-ledger consumers.
- **Action:** Run in an isolated Node process with the native adapter installed; see [CRDT convergence checks](../../docs/crdt-convergence.md).
- **Requires:** The `svelte-realtime/sim` export from this release.
- **Compatibility:** Additive API; drop/corrupt modes deliberately fail.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: structured error parameters

`LiveError` and `RpcError` carry bounded JSON `params` and `details` through RPC calls, uploads, SSR hydration and the `createTestEnv` harness, so an application can render localized error text from the code and its parameters while every existing caller keeps reading the same source-English `message` it reads today.

- **Affects:** Applications that show server errors to users or map error codes to their own messages.
- **Action:** None; pass `params` or `details` when throwing to use them.
- **Requires:** Nothing beyond this release on both server and client.
- **Compatibility:** Additive; error messages and codes are unchanged.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: one registered user type

Declaring `Register.user` once types the user on live contexts, socket data, guards, stream callbacks, uploads and generated stream options across the whole app, which removes repeated generic annotations, while bare `LiveContext` and `UploadContext` annotations in an app that registers nothing now default to `any` like callback inference does.

- **Affects:** TypeScript applications that annotate live contexts or read the connected user.
- **Action:** Add a `Register` declaration to type the user everywhere; keep an explicit generic where a bare annotation must stay `unknown`.
- **Requires:** TypeScript declarations from this release.
- **Compatibility:** Type-level only; runtime behavior is unchanged.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: upload flow control

Uploads now pause the sending client while `maxBufferedChunks` chunks wait for the handler and resume as `ctx.stream` is read, so a handler that awaits a slow sink receives every byte with default options, and the documented upload wire format lets clients outside the browser speak the same protocol.

- **Affects:** Applications that upload files or streams, and custom upload clients.
- **Action:** None for the bundled client; custom clients follow the upload wire format document.
- **Requires:** Server and client from this release for credits; a client from this release falls back to the previous format once per connection against an older server, and an older client that overflows the queue fails with `FLOW_BACKPRESSURE`.
- **Compatibility:** Additive; `FLOW_BACKPRESSURE` now fails only a sender that ignores its credit.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: delivery authorization

`realtime({ authorizeDelivery })` re-checks current access for every message to every recipient, including relayed, queued and replayed frames, stream snapshots and server requests, so a subscriber whose role, assignment or session was revoked stops receiving data and its connection closes.

- **Affects:** Applications whose access can change while a subscription is open.
- **Action:** None unless you opt in; configure the policy on every worker to use it.
- **Requires:** svelte-adapter-uws 0.6.0-next.97 or newer; with an older adapter a configured policy fails startup.
- **Compatibility:** Additive and off by default; publishes walk every local connection while a policy is installed.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: dead-letter capture receipts

A webhook dead-letter capture into a store that declares `keyedAdd: true` carries the failed delivery's idempotency key, so a store write whose reply was lost is repeated without creating a second record, a delivery captured twice is kept once, and every repeat gets back the original record ID as its receipt.

- **Affects:** Applications that enable the webhook dead-letter queue, and authors of custom dead-letter stores.
- **Action:** None for the built-in store; a custom store that honors `add({ key })` declares `keyedAdd: true`, as described in [docs/dead-letter-store.md](../../docs/dead-letter-store.md).
- **Requires:** Nothing beyond this release for the built-in store; a durable store without `keyedAdd` keeps one unkeyed write per capture.
- **Compatibility:** Failed deliveries of one webhook that share an idempotency key now collapse into one record in the built-in store.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: resumable erasure jobs

With `configureForget({ jobs })` every `live.forget` is recorded as its own job under a random reference before any data is touched, so an erasure that fails or dies part-way is listed by `listForgetJobs()` and finished by `resumeForgetJobs()`, one run at a time per job, with failing jobs backing off.

- **Affects:** Applications that erase user data with `live.forget`, especially with a durable erasure store.
- **Action:** Configure a job store and call `resumeForgetJobs()` at startup and on a schedule, or set `resumeIntervalMs`; in a cluster, run `live.forget` on every worker, since each process erases and retries its own in-memory state.
- **Requires:** Nothing beyond this release for the in-memory store; a store that survives restarts implements `ForgetJobStore`.
- **Compatibility:** Additive and off by default; with a job store, `live.forget` requires `tenantId` and its result carries `job`.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Added: background work metrics

`live.metrics` now reports cron, alarm, poll, derived, effect, outbound webhook and dead-letter work through one bounded schema (counts by result, run times, running and waiting items, oldest waiting age, exhausted retries), exported as `BACKGROUND_METRICS`, so a dashboard shows background work falling behind before throughput does.

- **Affects:** Operators who scrape `live.metrics` and alert on background work.
- **Action:** None; add the `svelte_realtime_background_*` series to dashboards and alerts.
- **Requires:** A registry gauge with `set` for the gauges.
- **Compatibility:** Additive; the existing cron series are unchanged.
- **Engineering detail:** [Added for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: adapter and extensions versions

This release declares `svelte-adapter-uws` `^0.6.0-next.97` as its peer and lists `svelte-adapter-uws-extensions` `0.6.0-next.65` in its compatibility tuple, so an application that keeps an older adapter gets a peer conflict on upgrade until it moves the adapter into that range together with realtime.

- **Affects:** Every application upgrading to this release.
- **Action:** Install `svelte-adapter-uws@0.6.0-next.97` together with this release; applications that use the extensions packages move them to `svelte-adapter-uws-extensions@0.6.0-next.65` at the same time.
- **Requires:** `svelte-adapter-uws` `^0.6.0-next.97`.
- **Compatibility:** Breaking for installs that keep an older adapter, and for extensions alarm stores older than `0.6.0-next.65`, which lack the execution methods `configureAlarm` now requires. The tuple is listed under [version compatibility](../../README.md#version-compatibility).
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: clustered smooth ownership

Clustered smoothed entities keep running with the Redis coordinator from `svelte-adapter-uws-extensions`, which declares no ownership version, on the pre-v1 ownership path with one warning, while a coordinator declaring `ownershipVersion: 1` gets fenced epoch ownership that stops a replaced owner's late broadcasts during a takeover.

- **Affects:** Clustered deployments that install a coordinator on `platform.smooth`.
- **Action:** None for the extensions Redis coordinator; a custom coordinator declares `ownershipVersion: 1` and implements [fenced ownership](../../docs/smooth-cluster.md), or resolves exactly `true` or `false` from both lease calls.
- **Requires:** Nothing beyond this release on the pre-v1 path; fencing needs a coordinator implementing `SmoothCluster` with `ownershipVersion: 1`.
- **Compatibility:** A coordinator declaring another version, missing a lease method, or answering a lease call with anything but `true` or `false` now fails closed.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: tenant-scoped erasure

When a tenant resolver, a `configureForget` store or an enabled webhook dead-letter store is configured, `live.forget(userId, opts)` now requires `opts.tenantId` and rejects with `INVALID_REQUEST` before purging anything, instead of silently erasing the untenanted scope and reporting success for a call that named no tenant.

- **Affects:** Multi-tenant applications and applications with a durable erasure or dead-letter store.
- **Action:** Pass `tenantId`, or an explicit `null` for the untenanted scope, on every `live.forget` call.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Breaking for calls that omitted the tenant under these configurations; unchanged otherwise.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: upload limits and context views

The upload frame cap now arrives on the first RPC or upload response so later uploads start at the full cap, `live.upload()` rejects a non-integer `maxBufferedChunks` at declaration, and RPC contexts expose their platform view as a plain object that inherits from the platform rather than read-only per-call properties.

- **Affects:** Applications that declare uploads with custom buffering or inspect `ctx.platform` properties.
- **Action:** Declare `maxBufferedChunks` as a positive integer; no other change is needed.
- **Requires:** Nothing beyond this release.
- **Compatibility:** An invalid `maxBufferedChunks` now fails at startup; the default upload quotas are covered in their own entry.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: cross-session upload quotas

`live.upload()` now bounds admitted uploads per signed-in user (16), per tenant (100) and per process (1,000), and unread buffered bytes per tenant and process, so one user or tenant holding stalled uploads across many sessions can no longer occupy the handler slots and memory every other caller needs.

- **Affects:** Applications with upload endpoints that run many uploads at once per user, tenant or process.
- **Action:** Raise `maxConcurrentPerUser`, `maxConcurrentPerTenant` or `maxConcurrentTotal` (or pass `Infinity`) where legitimate traffic exceeds the defaults, and stop handlers on `ctx.abortSignal` so a cancelled upload frees its slot.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Starts over a limit fail with `TOO_MANY_UPLOADS` or `OVERLOADED`, and an upload counts against its session until its handler returns.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: idempotency capacity per identity

The in-process `live.idempotent` store divides its 10,000 slots between tenants and identities and gives cron and alarms pools of their own, so a caller at its own share replaces only its own envelope-key result, every other limit refuses the new key, and no caller's traffic re-runs another caller's accepted effect.

- **Affects:** Applications using `live.idempotent` with the default in-process store.
- **Action:** Use a shorter `ttl`, a tenant resolver or a durable idempotency store when one identity keeps more than 100 results inside a tenant, or 1,000 without tenants, within the TTL, or when anonymous traffic can fill the store.
- **Requires:** Nothing beyond this release.
- **Compatibility:** A retry of a key its caller has replaced runs the handler again; a new key at a limit fails with `IDEMPOTENCY_CAPACITY` before its handler runs, with `retryAfter` when the caller's own share is full, and an offline replay told to wait longer than 30 seconds stays queued and is reported through `onReplayError`.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: bounded effects and webhooks

Each `live.effect` now runs at most 32 calls at once with 10000 queued and gives back a slot pending past 30 s, and each outbound webhook at most 64 deliveries with 10000 queued, so a stalled handler or endpoint holds bounded work, and a publish past both limits is rejected and reported.

- **Affects:** Applications with `live.effect` or `live.webhooks.outbound` handlers that can fall behind their source topics.
- **Action:** Set `timeoutMs` above the longest run, or to `Infinity`, on an effect whose calls legitimately run longer than 30 s or must never overlap; raise `maxConcurrent` or `maxQueued` where a webhook carries more than 64 events per delivery time (128 events/s to a 500 ms endpoint) or an effect needs more than 32 calls at once.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Calls past the new limits are skipped and reported instead of piling up (webhook events through `onFailure`); an effect call pending past 30 s gives its slot back while its handler runs on, reported as `TIMEOUT`, so the next call can overlap it. Other behavior is unchanged.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: bounded RPC admission

Each worker now runs at most 32 calls per connection, 256 per function and 1024 in total, queues 32 per connection and 256 in all, refuses the rest at once with `OVERLOADED`, and the client keeps at most 256 calls awaiting a response, so a slow dependency holds bounded work instead of arrival rate times latency.

- **Affects:** Applications whose functions can run many calls at once on one worker or one connection, including parallel batches above 32 calls, and clients that keep more than 256 calls in flight.
- **Action:** Pass `ctx.abortSignal`, which fires at a call's deadline or when its connection closes, to slow work. Raise the limits with `realtime({ rpc })`, per function with `live(fn, { perRouteConcurrent })`, or on the client with `configure({ rpc: { maxPending } })` where legitimate load exceeds them (`0` disables a limit); handle `OVERLOADED`, which carries `reason` and `scope`, like other transient refusals.
- **Requires:** Server and client from this release for `reason` and `scope` on the client error.
- **Compatibility:** Calls past the limits are refused before they run instead of piling up; a function's `timeout` is now the call's budget on both ends, and the server fires `ctx.abortSignal` within 250 ms after it. Other behavior is unchanged.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Changed: stream resume from a replay buffer

A stream that declares `replay` now takes a replay on resume only when the buffer can answer the whole gap, and otherwise reloads through its loader instead of calling `delta.fromSeq`, so a trimmed or restarted buffer no longer leaves stale rows and a `live.flag` resumes to its newest value.

- **Affects:** Applications that declare streams with `replay` and expose `platform.replay`, especially those that also declare `delta.fromSeq`.
- **Action:** Declare a stream that resumes its gaps through `delta.fromSeq` without `replay` and publish its events with their own `seq`; where `platform.replay` is installed, a stream that declares both resumes from the buffer or its loader, and it warns in dev.
- **Requires:** Nothing beyond this release. Against an older server the client discards a crud or latest replay with a hole and reloads, while a set stream applies its newest entry; that includes an older server's `delta.fromSeq` answer, which is not marked, when its events are not numbered on from the cursor.
- **Compatibility:** Behavior change: with a replay buffer, a buffer that cannot answer, including one whose store is unreachable such as during a Redis outage, now sends the resume to the loader, not to `delta.fromSeq`; a stream without a buffer uses `delta.fromSeq` as before.
- **Engineering detail:** [Changed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: resume cursor of fromSeq streams

A stream that resumes through `delta.fromSeq` keeps its own cursor when an answer carries no numbered event, instead of taking the replay buffer's unrelated counter, so a later resume no longer delivers events the client already has again or skips the events between its cursor and that counter.

- **Affects:** Applications whose streams declare `delta.fromSeq` without `replay` on a platform that installs `platform.replay`.
- **Action:** None for a stream that publishes its live events with their own `seq`; one that does not publishes them with it, since the client's cursor otherwise follows the adapter's counter rather than the numbering `delta.fromSeq` reads.
- **Requires:** A server from this release.
- **Compatibility:** Fixed behavior; an incremental answer, from the buffer or `delta.fromSeq`, no longer moves the cursor back, and a loader answer still sets it.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: delta hooks scoped to their topic

`delta.version`, `delta.diff` and `delta.fromSeq` now receive the `ctx` and arguments the stream's loader receives after their cursor, so a stream whose topic factory returns `'audit:' + orgId` answers a resume with the changes of its own topic, where the documented `delta.fromSeq` example read every organization's events.

- **Affects:** Applications that declare `delta.diff` or `delta.fromSeq` on a stream with a topic factory, especially those that copied the documented example.
- **Action:** Filter such a hook by the `ctx` and arguments it now receives, as the README example does; one declared with at most one parameter warns in dev.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Additive for a hook that declares only its cursor; a hook whose second parameter has a default value now receives `ctx` in that slot, so move such a parameter into a closure.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: replay buffer for every publisher

A publish to a replay stream's topic now writes the buffer when the publishing process has no local subscriber of it, as with a tenant-scoped publish from a cron leader or a resolved factory topic, so a resume answered from the buffer no longer misses events published on another replica.

- **Affects:** Clustered applications with replay streams, especially multi-tenant ones and those whose topics come from a factory.
- **Action:** None; a topic factory with a leading literal namespace and one argument per segment, such as one returning `'chat:' + roomId`, is covered from its declaration.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Fixed behavior; these publishes now go through `platform.replay.publish`, which numbers them in the buffer. A process that has not loaded the stream's module still publishes without it.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: presence and multiplayer consistency

Sticky presence, multiplayer selections and multiplayer locks now stay consistent between live members, late joiners and replicas, because payloads keep their exact bytes on the Redis roster, refused entries are never broadcast, oversized lock names are rejected, and updates for departed or erased members stop instead of reappearing later.

- **Affects:** Applications using presence, multiplayer selections or locks, especially across replicas.
- **Action:** None.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Unchanged contract; lock names over 128 UTF-8 bytes are now rejected.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: tenant isolation and subscription release

Erasure, push routing and dead-letter records stay within their own tenant, and a stream or document subscription that is refused, closed or failed now releases its adapter membership and grant, so a later subscribe on the same socket is judged afresh and sibling streams keep their events.

- **Affects:** Multi-tenant applications and applications whose stream loaders can refuse a subscriber.
- **Action:** None.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Unchanged contract; refused subscriptions no longer leave membership behind.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: metrics and documentation accuracy

RPC and upload metrics now count calls refused before they run and record exactly one terminal outcome per upload, structured error details survive upload reauthorization, and the documented extension import paths and alarm example name modules the extensions package really exports, so copied examples resolve without edits.

- **Affects:** Operators reading RPC and upload metrics, and developers copying extension examples.
- **Action:** None; dashboards may show refused calls that were previously missing.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Unchanged contract; metric totals now include refused calls.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: unchanged client rows stay silent

A versioned CRUD row that the client already holds no longer notifies Node subscribers again, so repeated stale events avoid downstream work, while optimistic confirmations and accepted or refused queued writes still settle and native count gates pin batching, encoding and replay work.

- **Affects:** Node subscribers to versioned streams and package maintainers.
- **Action:** None.
- **Requires:** The client from this release.
- **Compatibility:** Matches browser behavior; optimistic settlement is unchanged.
- **Engineering detail:** [Fixed for 0.6.0-next.92 in the complete changelog](../../CHANGELOG.md#060-next92---2026-11-06).

### Fixed: SvelteKit 2 development finds live functions

Under `vite dev` on SvelteKit 2, a server `load` or endpoint that calls a stream's `.load()` now finds its live functions on a cold or warm Vite cache instead of failing with `NOT_FOUND`, because the server runtime is loaded once in Node and shared by routes, WebSocket hooks and live-module reloads.

- **Affects:** SvelteKit 2 applications that call `.load()` during SSR in development.
- **Action:** None.
- **Requires:** Nothing beyond this release.
- **Compatibility:** Unchanged contract; production builds and SvelteKit 3 already found them.

- **Affects:** Applications that follow the typed error transport recipe in a shared `src/hooks.js`.
- **Action:** None; rebuild to get the smaller bundle.
- **Requires:** Nothing beyond this release.
