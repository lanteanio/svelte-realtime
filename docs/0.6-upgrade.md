# Migration guide: svelte-realtime 0.5.x to 0.6.x

[migration index](../MIGRATION.md) | [README](../README.md) |
[release history](../CHANGELOG.md) |
[adapter ecosystem sequence](https://github.com/lanteanio/svelte-adapter-uws/blob/dev/docs/migrations/ecosystem-0.5-to-0.6.md)

> **Lifecycle:** active prerelease transition. New 0.6 release candidates may
> add entries until the stable line is promoted.

This guide covers the current 0.6 source, including Unreleased changes. Entries
marked unpublished in the [version history](../CHANGELOG.md) remain candidates;
the [release manifest](release-manifest.md) records published artifacts. Check
your starting version before applying an action below. Apps coming from 0.4
first follow the [0.4 to 0.5 guide](../MIGRATION.md#04x-to-05x). The
changelog remains the exhaustive release log; this guide collects only changes
that require an application or operator choice, and states explicitly which
surfaces need none.

Sections up to [promotion and rollback](#promotion-and-rollback) apply to an
application upgrading from 0.5.14. An application already running an earlier
0.6 prerelease also follows
[changes since an earlier 0.6 prerelease](#changes-since-an-earlier-06-prerelease),
which covers surfaces that 0.5 never shipped.

`test/migration-rehearsal.test.js` rehearses the room action rename and the
unknown-path default below. The unedited 0.5 module is served by the 0.5.14
artifact, repacked from its recorded source commit and matched against the
[release manifest](release-manifest.md); the packed candidate refuses the same
module at declaration, and the edited module serves a real WebSocket client.

## Prerequisites and supported tuples

Before editing source, keep the stable lockfile and a deployable artifact for
the currently routed release. The realtime package and both sibling packages
require Node 22 or newer. The 0.6 line requires `svelte-adapter-uws`
`^0.6.0-next.96` as a peer; extensions, when used, must come from the same
compatibility row.

| Purpose | Realtime | Adapter | Extensions |
| --- | --- | --- | --- |
| Rollback baseline | exact `0.5.14` | `0.5.x` (0.5.11 or later) | `0.5.x` |
| Upgrade candidate | exact `0.6.0-next.*` | matching `0.6.0-next`, at least `0.6.0-next.96` | matching `0.6.0-next` |

The [compatibility table](../README.md#version-compatibility) is the authority
for the exact current prerelease tuple. Do not copy the wildcards in this
explanatory table into a lockfile, and do not combine cells from different rows.
Upgrade the adapter, then extensions, then realtime, following the
[adapter ecosystem sequence](https://github.com/lanteanio/svelte-adapter-uws/blob/dev/docs/migrations/ecosystem-0.5-to-0.6.md).

## Required source edits

### Installation

The coordinated package tuple and native runtime prerequisites determine whether
a scaffold can build and start.

**Action required:** select a published compatible tuple, meet the documented
Node/build and platform floors, and run the installed
[native preflight](../README.md#version-compatibility) before building. Candidate
commands in that section require the tuple to be published first.

### Connection cleanup

The runtime releases stream membership on unsubscribe and connection state on
close when all routing hooks are installed.

**Action required:** export or forward `message`, `unsubscribe` and `close`
as shown in [manual setup](../README.md#step-3-create-the-websocket-hooks-file),
including the factory's returned cleanup hooks when using `realtime()`.

### Testing

The test helpers use `svelte-realtime/testing` and
`svelte-realtime/testing/client` instead of the former test subpaths.

**Action required:** update imports using the [testing migration](../MIGRATION.md#svelte-realtimetest-renamed-to-svelte-realtimetesting-and-test-client-to-testingclient).

Tests that mock `svelte-adapter-uws/client` must return the full connection
object the adapter's `connect()` returns.

**Action required:** update adapter mocks using the
[next.91 connection-mock details](../CHANGELOG.md#060-next91---2026-10-13).

### Authorization

Authenticated guards reject empty or invalid identity values, and unknown RPC
paths return generic authorization denials by default.

**Action required:** use a validated application identity and handle denial codes;
review [authentication guards](../README.md#authentication-shorthand-on-guards)
and [path masking](../README.md#masking-path-existence-masknotfound) before opting
into explicit missing-path replies.

### Rooms

Room actions cannot replace generated client members, and sends in rooms with
presence require the sender's room membership.

**Action required:** rename conflicting actions and retain the joined room while
sending; follow the [room](../README.md#rooms) contract. `live.room()` reserves
`data`, `presence`, `cursors`, `owner` and `rooms` even when the corresponding
surface is disabled, and throws at declaration when an action uses one of these
names. Cursor-only rooms without presence still allow sends without a
membership.

### Offline mutations

Offline callbacks receive the call-time JSON values, and a throwing or async
`beforeReplay` drops that queued mutation.

**Action required:** keep `beforeReplay` synchronous, handle replay failures,
and adapt callbacks that depended on mutable object identity using the
[replay contract](../README.md#conflict-resolution-replayed-mutations).

### Upload cancellation

Upload handlers expose cancellation as `ctx.abortSignal`, with `ctx.signal`
retained as a deprecated cancellation alias during 0.x.

**Action required:** migrate upload cancellation reads to `abortSignal`;
see [streaming uploads](../README.md#streaming-uploads). The upload alias is not
the callable targeted-signal helper available to ordinary live handlers.

### Streams and reconnect

Reconnect, pagination and optimistic settlement keep authoritative stream data
consistent, while subscription release is idempotent across pending joins.

**Action required:** no source migration for these fixes; use the documented
[attach lifecycle](../README.md#attach-lifecycle-storephase-attach-detach) and
[optimistic updates](../README.md#optimistic-updates), and test disconnect and
error handling against your application's configured limits.

## Default changes

| Surface | 0.5 behavior | 0.6 behavior | Required decision |
| --- | --- | --- | --- |
| Unknown RPC paths | Explicit not-found replies | Generic authorization denials for text, batch, binary and upload calls | Set `maskNotFound: false` only if clients need missing-path replies |
| `live.lock` waiters | Unbounded queue per key | At most 1000 queued callers per key; timed-out waiters leave the queue | Handle `LOCK_QUEUE_FULL` or set `maxWaitersPerKey` |
| Room action names | Any valid name, including `data` and `presence` | `data`, `presence`, `cursors`, `owner` and `rooms` are reserved; an action using one throws at declaration | Rename conflicting actions |

## Wire and storage compatibility

The realtime package owns no database schema of its own. Durable state belongs
to the store that holds it:

- Offline queues: 0.5 keeps queued mutations in memory only, so nothing
  persisted by 0.5 needs migration.
- Stores introduced during the 0.6 prereleases (durable alarms, offline
  persistence, outbound webhook dead letters) are covered under
  [changes since an earlier 0.6 prerelease](#changes-since-an-earlier-06-prerelease).

Client and server must come from the same release: wire frames carry new
fields (structured error `params` and `details`, upload credits, the upload
frame cap). Uploads tolerate one mismatch direction only: a client from this
release falls back to the previous upload format against an older server,
while an older client against a newer server sends without credits and fails
with `FLOW_BACKPRESSURE` when it overflows the receive queue. Use
[protocol rollout](../README.md#coordinated-protocol-rollout-and-rollback) to
bound mixed client bundles during a deploy.

## No action needed

- Reactive streams, reconnect and pagination: fixes only; see
  [streams and reconnect](#streams-and-reconnect).
- Shared documents, smoothed entities, protocol windows and DevTools: opt-in;
  see [optional capabilities](#optional-capabilities).
- Structured error `params` and `details`, `Register.user` typing and upload
  flow control: additive; existing callers keep working.
- Presence and subscription release fixes: behavior is corrected without
  source changes.

## Upgrade checklist

1. Record the current lockfile and deployable artifact for rollback.
2. Select the exact candidate tuple from the
   [compatibility table](../README.md#version-compatibility).
3. Apply every required source edit above that matches your application.
4. Review each default change and record the decision.
5. Coming from a 0.6 prerelease, also apply
   [changes since an earlier 0.6 prerelease](#changes-since-an-earlier-06-prerelease),
   migrating or snapshotting durable alarm rows and updating webhook receivers
   before upgrading senders.
6. Run your application's tests, then exercise reconnect, uploads and
   disconnect handling against the candidate.

## Promotion and rollback

Upgrade the adapter first, extensions second and realtime last, using the exact
packages from one compatibility row. Keep the previous lockfile, build artifact
and any store snapshot until the candidate has passed reconnect and replay
checks under production-shaped traffic.

To roll back, restore the complete 0.5 tuple in reverse order: realtime, then
extensions, then the adapter. Restore store snapshots where the store's owner
requires it, restart workers and force clients to reconnect so no 0.6 client
bundle talks to a 0.5 server. Never roll back one package into a mixed tuple.

## Changes since an earlier 0.6 prerelease

These surfaces did not exist in 0.5.14. An application coming from 0.5 that
adopts them starts on the current contract and needs no migration; an
application already running a 0.6.0-next release applies the matching action.

| Capability | Compatibility impact | Current guidance |
| --- | --- | --- |
| Tenant configuration | Required for custom configuration | [Use validated policy metadata](#tenant-configuration) |
| Tenant-scoped erasure | Required with a tenant resolver or durable erasure store | [Name the tenant](#tenant-scoped-erasure) |
| Room owners and multiplayer | Required for multiplayer action names and owner-room sends | [Reserved members and joined sends](#room-owners-and-multiplayer) |
| Room field surfaces | Required for typing, selections and locks | [Supply presence](#room-field-surfaces) |
| Room share codes | Required for older codes | [Reissue or validate codes](#room-share-codes) |
| Outbound webhook receivers | Required | [Timestamped signatures](#webhook-signatures) |
| Aggregate privacy | Required for noise strategies | [Configure the secret](#aggregate-privacy) |
| Offline persistence | Required for custom stores; retention default changed | [Durable writes, retention and erasure](#offline-persistence) |
| Durable alarms | Required for custom stores | [Atomic claims and stable identity](#durable-alarms) |
| Simulation harness | Required for fault options | [Renamed fault options](#simulation-fault-options) |

### Tenant configuration

`live.tenant(id, config)` validates and copies immutable policy metadata.
Unknown fields and `null` now throw `VALIDATION` during registration.

**Action required:** replace arbitrary configuration objects with the documented
[`TenantConfig` shape](../README.md#multi-tenancy-livetenant). Remove the unsupported `quota` option and configure actual
admission limits in the owning adapter, extension or application. Metadata alone
does not enforce limits or provide tenant fairness.

### Tenant-scoped erasure

With a tenant resolver, a `configureForget` store or an enabled webhook
dead-letter store, `live.forget(userId)` without a tenant rejects with
`INVALID_REQUEST` before purging anything; it previously erased the
untenanted scope.

**Action required:** pass `{ tenantId }`, or `{ tenantId: null }` for the
untenanted scope, on every `live.forget` call; see
[right to erasure](../README.md#right-to-erasure-liveforget).

### Room owners and multiplayer

Sends in rooms with an owner require the sender's room membership, as in rooms
with presence. `live.multiplayer()` reserves every member its generated client
namespace provides: `data`, `presence`, `cursors`, `owner`, `status`, `move`,
`reportViewport`, `identify`, `room`, `watch`, the field views `typing`,
`locks`, `selections` and `reactions`, their send methods `setTyping`,
`acquireLock`, `releaseLock`, `setSelection` and `react`, and the internal
`_setField` and `_emitReaction`. It throws at declaration when an action uses
one of these names.

**Action required:** rename conflicting multiplayer actions, keep the room
joined with `room()` while sending, and use `watch()` for a read-only observer;
follow the [multiplayer](../README.md#multiplayer) contract.

### Room field surfaces

Typing, selections and locks require a presence function so late joiners can
recover the retained fields.

**Action required:** supply presence when enabling those
[field surfaces](../README.md#field-surfaces-typing-selections-locks-reactions);
reactions alone do not require presence. Multiplayer presence rejects lock
names over 128 UTF-8 bytes.

### Room share codes

The stronger short-code key derivation changes codes created before next.90,
and an old code can decode to a different room identity.

**Action required:** validate every decoded identity against your store, or
issue fresh codes and retire old links; see
[share-code validation](../README.md#unguessable-join--share-codes-shortcodes)
and the [next.90 breaking notice](../CHANGELOG.md#060-next90---2026-07-30).

### Webhook signatures

Outbound webhook signatures include a timestamp in the signed message.

**Action required:** update receivers to verify
`HMAC_SHA256(secret, timestamp + '.' + rawBody)` and apply the documented
replay-window checks in [webhook delivery](../README.md#delivery).

### Aggregate privacy

The `perturb` and `hybrid` strategies require a server privacy secret,
while cohort suppression alone does not.

**Action required:** configure `realtime({ privacySecret })` before enabling
noise, and review the [privacy boundary](../README.md#privacy-cohort-suppression-and-keyed-noise);
these controls do not establish a differential privacy guarantee or enforce a
privacy budget.

### Offline persistence

Custom persistence resolves writes only after storage succeeds, and queued records have a finite
retention window with explicit logout erasure.

**Action required:** make `OfflineStore.put` resolve after storing the value and reject failed writes,
choose `offline.retentionMs` if the seven-day default is unsuitable, and await
`clearOffline()` during account cleanup; see
[durable persistence](../README.md#durable-persistence-survive-a-reload).
Custom stores shared with other writers must implement atomic `deleteExpired`
to preserve fresh records written by another tab.

Mutations persisted by a prerelease are replayed; rows without an expiry use
their `queuedAt` time and the seven-day default.

### Durable alarms

Durable alarms require ordered generations and retained execution records so
failed or interrupted callbacks remain inspectable for explicit retry.

**Action required:** deploy a compatible extensions store or implement the
complete generation, claim, settlement, inspection and requeue contract linked
from [per-room alarms](../README.md#per-room-alarms); migrate stored rows and
upgrade legacy workers together. Await scheduling/cancellation, choose a stable
`alarm.id` before renaming a handler, and make external effects idempotent
before an operator retries uncertain work; callback effects are not exactly once.

Alarm rows already migrated to the generation format need the store's own
rollback step when rolling back to a prerelease.

### Simulation fault options

Simulation swarms use `faultMode`, `faultProbability` and `faulted`.

**Action required:** rename the options using the
[next.90 option renames](../CHANGELOG.md#060-next90---2026-07-30); regenerate
application-owned simulation goldens only after reviewing the intended change.

### Prerelease default changes

| Surface | Earlier prerelease behavior | Current behavior | Required decision |
| --- | --- | --- | --- |
| `live.tenant(id, config)` | Arbitrary configuration retained | Validated, frozen metadata; unknown fields and `quota` throw `VALIDATION` | Use the `TenantConfig` shape |
| `live.forget` with a tenant resolver or durable erasure store | An omitted tenant erased the untenanted scope | Rejects with `INVALID_REQUEST` before purging | Pass `tenantId`, or `null` for the untenanted scope |
| Persisted offline mutations | Kept until replayed | Expire after seven days | Set `offline.retentionMs` if seven days is unsuitable |
| Outbound webhook signatures | HMAC over the body | HMAC over the timestamp, a dot and the raw body | Update receivers before senders |

## Optional capabilities

### Collaborative state

Shared documents provide conflict-free editing, and smoothed entities provide
server-authoritative simulation with client prediction.

**Action required:** none unless adopting these features; follow
[shared documents](../README.md#shared-documents) or
[smoothed entities](../README.md#smoothed-entities), including their Svelte 5
requirements and application-owned persistence policies.

### Operations

Protocol windows let deployments coordinate client bundles, while operational
events and DevTools expose connection and failure state.

**Action required:** none for protocol opt-in; configure matching versions and
rollout bounds using [protocol rollout](../README.md#coordinated-protocol-rollout-and-rollback).
Update diagnostic consumers against the current
[operational event sink](../README.md#operational-event-sink), and enable
[DevTools payload capture](../README.md#devtools) only when needed.
