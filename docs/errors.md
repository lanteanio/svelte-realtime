# Runtime error reference

Search this page with the exact error code, event name, stable ID, or the beginning of the message you saw.

This file is generated by `npm run generate:errors` from the runtime error registry (`src/error-registry.js`), the operator guidance in `scripts/error-guidance.js`, and a parse of every emission in `src/**/*.js`. Do not edit it by hand. Coverage at generation time:

- 7 [stable IDs](#stable-ids) with full guidance. Their runtime messages append the ID and the help route to this page.
- 42 [runtime error codes](#runtime-error-codes) (`LiveError` on the server, `RpcError` on the client, error replies on the wire), every one with cause, consequence, automatic recovery and next action.
- 32 [failure events](#operational-events) (warn, error or fatal), every one with full guidance, and 4 [informational events](#informational-events) listed without guidance because they report normal operation.
- 102 [console lines](#console-lines) indexed by searchable text. A server, Vite or shared console warning or error is either printed through the registry with a stable ID or carries a recorded reason why it needs no guided entry; browser and scaffolder output is listed without one.
- 33 emission sites with a computed code, event or message, each with a recorded reason, under [dynamic emission sites](#dynamic-emission-sites).

Generation fails on a new error code or a new event emitted at warn, error or fatal without guidance, on a new console warning or error without a stable ID or a recorded reason, and on a new computed emission site without a recorded reason. It also fails on guidance or a reason that no longer matches anything the runtime emits. An event emitted with a severity the parser cannot resolve counts as a failure event. Codes and messages are followed through local constants and through helper functions to their call sites before a site counts as computed.

This is the svelte-realtime part of the ecosystem index. The sibling packages generate and ship their own references:

- [svelte-adapter-uws errors](https://github.com/lanteanio/svelte-adapter-uws/blob/dev/docs/errors.md)
- [svelte-adapter-uws-extensions errors](https://github.com/lanteanio/svelte-adapter-uws-extensions/blob/dev/docs/errors.md)

Message patterns show the literal text the runtime prints. `<name>` stands for a computed value, named after the variable or property it comes from; search for the literal text around it. Escaped `\n` and `\r` stand for actual newlines and carriage returns. Code and event anchors stay stable when message text changes.

<a id="realtime-err-invalid-user-id"></a>
### `REALTIME-ERR-INVALID-USER-ID`

- Runtime code: [`INVALID_USER_ID`](#live-error-invalid-user-id)
- Event: `ctx.signal.invalid-user-id`
- Message prefix: `ctx.signal:`
- Cause: ctx.signal(userId, ...) received a value that is not a non-empty string of at most 256 characters, or it contains a control character, double quote, or backslash.
- Consequence: The signal is not published and the caller receives an INVALID_USER_ID LiveError.
- Automatic recovery: None; malformed identity input is not retried.
- Next action: Pass the canonical validated user ID used by enableSignals(). Do not retry the same malformed value.
- Runtime help: `docs/errors.md#realtime-err-invalid-user-id`
- Runtime sources: [`src/server/ctx.js`](../src/server/ctx.js)

<a id="realtime-err-live-resolve"></a>
### `REALTIME-ERR-LIVE-RESOLVE`

- Runtime code: none
- Event: `vite.live.resolve-failed`
- Message prefix: `[svelte-realtime] Could not resolve $live/`
- Cause: A $live/<module> virtual import has no matching JavaScript or TypeScript file under the configured live directory.
- Consequence: The requested virtual module cannot load, so development or the build stops at that import.
- Automatic recovery: Vite resolves the import again after the module graph changes or the command is rerun.
- Next action: Correct the import path, add the matching live module, or configure the live directory.
- Runtime help: `docs/errors.md#realtime-err-live-resolve`
- Runtime sources: [`src/vite/plugin.js`](../src/vite/plugin.js)

<a id="realtime-err-upload-start-limit"></a>
### `REALTIME-ERR-UPLOAD-START-LIMIT`

- Runtime code: [`PAYLOAD_TOO_LARGE`](#live-error-payload-too-large)
- Event: `upload.pending-size.exceeded`
- Message prefix: `upload exceeds limit during start`
- Cause: Upload bytes crossed the protected pending-phase cap before the endpoint handler and its options finished resolving.
- Consequence: The upload is aborted before its endpoint handler begins and returns PAYLOAD_TOO_LARGE.
- Automatic recovery: None; the aborted stream cannot be resumed.
- Next action: Reduce the initial or pending upload volume and retry with a new stream.
- Runtime help: `docs/errors.md#realtime-err-upload-start-limit`
- Runtime sources: [`src/server/upload.js`](../src/server/upload.js)

<a id="realtime-err-upload-max-size"></a>
### `REALTIME-ERR-UPLOAD-MAX-SIZE`

- Runtime code: [`PAYLOAD_TOO_LARGE`](#live-error-payload-too-large)
- Event: `upload.max-size.exceeded`
- Message prefix: `upload exceeds maxSize`
- Cause: The received upload bytes exceeded the maxSize configured by the resolved upload handler.
- Consequence: The upload is aborted and returns PAYLOAD_TOO_LARGE without invoking or completing the handler.
- Automatic recovery: None; the aborted stream cannot be resumed.
- Next action: Reduce the upload or deliberately raise maxSize, then start a new upload.
- Runtime help: `docs/errors.md#realtime-err-upload-max-size`
- Runtime sources: [`src/server/upload.js`](../src/server/upload.js)

<a id="realtime-err-room-history-capture"></a>
### `REALTIME-ERR-ROOM-HISTORY-CAPTURE`

- Runtime code: none
- Event: `room.history.capture-failed`
- Message prefix: `[svelte-realtime] history capture threw; suppressing further capture errors for this room`
- Cause: The `history.capture` function of a `live.room` threw while recording the state after a successful action.
- Consequence: The action still succeeds and its result is returned, but no history entry is recorded for it, so a later `ctx.compensate` that rewinds to that moment evaluates against the previous entry. Later capture failures in the same room are not printed.
- Automatic recovery: None for the missed entry. The next action records again, and a capture that stops throwing records normally.
- Next action: Fix the capture function using the error printed with this line; it must return a snapshot of the room state without throwing. Restart the process to see further capture errors after fixing.
- Runtime help: `docs/errors.md#realtime-err-room-history-capture`
- Runtime sources: [`src/server/room.js`](../src/server/room.js)

<a id="realtime-err-doc-persist"></a>
### `REALTIME-ERR-DOC-PERSIST`

- Runtime code: none
- Event: `doc.persist.failed`
- Message prefix: `[svelte-realtime] document persistence failed:`
- Cause: The `persist.load` or `persist.store` hook of a `live.doc` declaration threw or rejected, and the declaration has no `onError` handler. The line names the declaration, the operation and the topic.
- Consequence: A failed store leaves the document dirty in memory; it is not durable until a store succeeds and the replica is not unloaded meanwhile. A failed load leaves the document without its stored state.
- Automatic recovery: A failed store is retried on the `debounceMaxWait` cadence, printing this line on every failed attempt. A failed load is not retried by this line.
- Next action: Fix the storage backend or the hook using the error printed with this line. Pass `onError` to the declaration to route these failures into your own logging or alerting.
- Runtime help: `docs/errors.md#realtime-err-doc-persist`
- Runtime sources: [`src/server/crdt.js`](../src/server/crdt.js)

<a id="realtime-err-lazy-registration"></a>
### `REALTIME-ERR-LAZY-REGISTRATION`

- Runtime code: none
- Event: `lazy.registration.failed`
- Message prefix: `[svelte-realtime] Failed to resolve lazy registration for`
- Cause: Loading a lazily registered live module threw while the server resolved its deferred cron, derived, effect, webhook, aggregate or room-action registrations.
- Consequence: Nothing at that path is registered for the life of the process: its cron never runs, its derived stream or effect never reacts, and calls to its room actions answer NOT_FOUND. Other lazy registrations still resolve.
- Automatic recovery: None. Lazy registrations resolve once per process and the failed entry is not retried.
- Next action: Fix the module error printed with this line, then restart the server.
- Runtime help: `docs/errors.md#realtime-err-lazy-registration`
- Runtime sources: [`src/server/lazy.js`](../src/server/lazy.js)

<a id="live-error-alarm-capacity"></a>
### `ALARM_CAPACITY`

- Cause: A `ctx.setAlarm(at)` call needs a new alarm slot while this process already holds its limit of 100,000 pending or reserved alarms. Rescheduling a room that already has an alarm does not count against the limit.
- Consequence: The promise returned by `ctx.setAlarm` rejects with an ALARM_CAPACITY LiveError. No new alarm is scheduled, and alarms that were already acknowledged stay in place.
- Automatic recovery: None. The refused schedule is not retried.
- Next action: Await `ctx.setAlarm` and handle the rejection. Delete alarms for rooms that no longer need them, or spread rooms over more instances, then schedule again.
- Message patterns: <code>[svelte-realtime] alarm registry reached its pending alarm limit</code>
- Owning sources: [src/server/alarm.js](../src/server/alarm.js)

<a id="live-error-cancelled"></a>
### `CANCELLED`

- Cause: The client called `cancel()` on an upload handle or aborted its signal, or the server received the client's cancel frame for an upload that is still running.
- Consequence: On the client, the upload promise rejects with RpcError CANCELLED. On the server, the handler's upload iterator and signal abort with a CANCELLED LiveError, and buffered chunks are dropped.
- Automatic recovery: None. A cancelled upload stream cannot be resumed.
- Next action: Treat it as a deliberate stop. Release any partial state in the handler when its signal aborts. To send the data again, start a new upload.
- Message patterns: <code>upload cancelled</code>; <code>upload cancelled by client</code>
- Owning sources: [src/client/upload.js](../src/client/upload.js), [src/server/upload.js](../src/server/upload.js)

<a id="live-error-connection-closed"></a>
### `CONNECTION_CLOSED`

- Cause: The client connection closed for good: an explicit close, a terminal close code, a failed auth preflight, or no reconnect attempts left. On the server, the socket closed while a subscribe, document sync or smooth sync was still running.
- Consequence: Pending and new RPCs, uploads, `loadMore()` calls and stream subscribes reject with RpcError CONNECTION_CLOSED. Streams keep their data but switch to the error state. Server syncs throw a LiveError and release what they held.
- Automatic recovery: None. Nothing reconnects after the connection closes for good, and `configure({ url, auth })` is ignored from then on.
- Next action: Show the user that the connection is offline. Find out why it closed (auth, close code, retry budget), fix that, then call the adapter `connect()` explicitly to open a new connection.
- Message patterns: <code>Connection permanently closed</code>; <code>WebSocket closed</code>; <code>WebSocket closed during document sync</code>; <code>WebSocket closed during smooth sync</code>
- Owning sources: [src/client-multiplayer.svelte.js](../src/client-multiplayer.svelte.js), [src/client/connection.js](../src/client/connection.js), [src/client/internal-state.js](../src/client/internal-state.js), [src/client/rpc.js](../src/client/rpc.js), [src/client/stream.js](../src/client/stream.js), [src/client/upload.js](../src/client/upload.js), [src/server/crdt.js](../src/server/crdt.js), [src/server/dispatch.js](../src/server/dispatch.js), [src/server/smooth.js](../src/server/smooth.js)

<a id="live-error-disconnected"></a>
### `DISCONNECTED`

- Cause: The socket dropped or was replaced while a request was in flight, or a request outlived its timeout by a margin that points to device sleep. On the server, the client socket closed during an upload.
- Consequence: Sent RPCs and uploads reject with RpcError DISCONNECTED. A stream shows the error. On the server, the upload handler's iterator and signal abort with a DISCONNECTED LiveError, and no reply is sent.
- Automatic recovery: The adapter reconnects, streams subscribe again with backoff, and unsent calls keep waiting. Offline-queue replays stay queued. Other RPCs and uploads are not retried.
- Next action: Retry calls that are safe to repeat, ideally with an idempotency key, or enable the offline queue. Start uploads again from the beginning. Check the network or proxy if this happens often.
- Message patterns: <code>Connection interrupted (device sleep)</code>; <code>WebSocket connection lost</code>; <code>WebSocket connection replaced</code>; <code>connection closed</code>

- Automatic recovery: None. The dropped mutation is not re-queued.
- Next action: Raise `offline.maxQueue` if long offline periods are expected, coalesce repeated edits, and handle `onReplayError` to tell the user what was lost.
- Message patterns: <code>Offline queue overflow - oldest mutation dropped</code>
- Owning sources: [src/client/offline.js](../src/client/offline.js)

<a id="live-error-rate-limited"></a>
### `RATE_LIMITED`

- Cause: A `live.rateLimit` or registry `rateLimits` bucket is exhausted, the limiter reaches its cap on tracked identities, or a smooth client re-syncs more often than its per-identity window allows.
- Consequence: The call is refused before the handler runs. The client receives an RpcError carrying only the code and message. A server-side direct call receives the LiveError, which carries `retryAfter` in milliseconds.
- Automatic recovery: None. Buckets refill as their window passes, but refused calls are not retried.
- Next action: Back off on the client with your own delay; the client error does not say when the bucket refills. Server code can wait for `retryAfter`. If legitimate traffic is refused, tune points and window or look for clients calling in a loop.
- Message patterns: <code>Too many concurrent rate-limit identities</code>; <code>Too many requests</code>; <code>smooth re-sync rate exceeded (max 5 per 1000ms per identity); back off and retry</code>
- Owning sources: [src/server/dispatch.js](../src/server/dispatch.js), [src/server/rate-limit.js](../src/server/rate-limit.js), [src/server/smooth.js](../src/server/smooth.js)

<a id="live-error-service-unavailable"></a>
### `SERVICE_UNAVAILABLE`

- Cause: A function wrapped with `live.breaker` is called while its circuit breaker is open and no `fallback` is configured.
- Consequence: The call throws a SERVICE_UNAVAILABLE LiveError without running the wrapped function, and the client receives an RpcError. A `breaker.open` operational event is emitted once per open period.
- Automatic recovery: None in this library. Calls pass again once the breaker itself closes on its own reset schedule.
- Next action: Check the dependency named in the `breaker.open` event. Consider a `fallback` for degraded responses, and retry after a delay.
- Message patterns: <code>Service is temporarily unavailable, try again shortly</code>
- Owning sources: [src/server/breaker.js](../src/server/breaker.js)

<a id="live-error-source-error"></a>
### `SOURCE_ERROR`

- Cause: The upload source fails while being read on the client, for example a Blob read error or a ReadableStream that errors, with no server response yet.
- Consequence: The upload handle rejects with a SOURCE_ERROR RpcError carrying the original error message. A cancel frame is sent so the server discards the partial upload.
- Automatic recovery: None. The upload is not retried.
- Next action: Check the file or stream source the app passed in, then start a new upload. Show the user that the file could not be read.
- Message patterns: computed at every site (see [dynamic emission sites](#dynamic-emission-sites)).
- Owning sources: [src/client/upload.js](../src/client/upload.js)

<a id="live-error-stale"></a>
### `STALE`

- Cause: During offline replay a queued mutation is older than `offline.maxAge` or its retention, is refused by `beforeReplay` or the `replay` function, or has arguments that cannot be serialized.
- Consequence: The mutation is dropped without being sent. Its promise rejects with a STALE RpcError, sometimes with a `cause`, and `offline.onReplayError` is notified.
- Automatic recovery: None. Dropped mutations are not re-queued.
- Next action: Check `maxAge`, retention, `beforeReplay` and `replay` logic. Make `beforeReplay` synchronous and non-throwing, and surface dropped edits to the user via `onReplayError`.
- Message patterns: <code>Offline mutation dropped by beforeReplay filter</code>; <code>Offline mutation dropped by the replay function</code>; <code>Offline mutation dropped: beforeReplay returned a promise</code>; <code>Offline mutation dropped: beforeReplay threw</code>; <code>Offline mutation dropped: its stored args cannot be sent</code>; <code>Offline mutation dropped: the replay function gave it args that cannot be sent</code>; <code>Offline mutation expired</code>
- Owning sources: [src/client/misc.js](../src/client/misc.js)

<a id="live-error-stream-error"></a>
### `STREAM_ERROR`

- Cause: A stream subscribe fails with an error that is not already an RpcError, or `attach()` sees the stream fail with no recorded error.
- Consequence: The stream store enters its error state with a STREAM_ERROR RpcError. Any pending `attach()` rejects with it and later `attach()` calls reject immediately.
- Automatic recovery: The stream subscribes again after the next reconnect while it still has subscribers. Otherwise nothing retries.
- Next action: Inspect the error message and server logs for the subscribe. Fix the cause, then `detach()` and `attach()` or resubscribe.
- Message patterns: <code>Stream '&lt;path&gt;' failed to attach</code>; <code>Stream failed</code>
- Owning sources: [src/client/stream.js](../src/client/stream.js)

<a id="live-error-timeout"></a>
### `TIMEOUT`

- Cause: No reply arrives within the timeout for an RPC, batch, binary RPC, stream subscribe, `loadMore` or upload (default 30s via `configure({ timeout })`). On the server, a `live.push` recipient does not answer within `timeoutMs`.
- Consequence: The call rejects with an RpcError, or a LiveError for `live.push`. A timed-out upload sends a cancel frame. The server may still have run the request.
- Automatic recovery: None for RPCs, uploads or pushes. A timed-out stream subscribes again after the next reconnect. An offline replay that times out is dropped and reported.
- Next action: Check server handler latency and connection health, and raise the timeout if the work is legitimately slow. Make non-idempotent calls safe to retry with an idempotency key.
- Message patterns: <code>Batch timed out after &lt;value&gt;s</code>; <code>Binary RPC '&lt;path&gt;' timed out after &lt;value&gt;s</code>; <code>RPC '&lt;path&gt;' timed out after &lt;value&gt;s</code>; <code>RPC '&lt;rpc&gt;' timed out after &lt;value&gt;s</code>; <code>Stream '&lt;path&gt;' timed out after &lt;value&gt;s</code>; <code>Upload '&lt;path&gt;' timed out after &lt;value&gt;s</code>; <code>loadMore '&lt;path&gt;' timed out after &lt;value&gt;s</code>
- Owning sources: [src/client/rpc.js](../src/client/rpc.js), [src/client/stream.js](../src/client/stream.js), [src/client/upload.js](../src/client/upload.js), [src/server/push.js](../src/server/push.js)

<a id="live-error-too-many-uploads"></a>
### `TOO_MANY_UPLOADS`

- Cause: A new upload exceeds the per-session limit of uploads awaiting authorization, or the endpoint's `maxConcurrentPerSession` or `maxConcurrentTotal` limit.
- Consequence: The upload is refused before its handler runs. The client upload handle rejects with a TOO_MANY_UPLOADS RpcError.
- Automatic recovery: None. The refused upload is not queued or retried.
- Next action: Limit concurrent uploads in the client and wait for active ones to finish. Raise the endpoint concurrency options if the load is legitimate.
- Message patterns: <code>too many concurrent uploads</code>; <code>too many concurrent uploads on this session</code>; <code>too many uploads awaiting authorization on this session</code>
- Owning sources: [src/server/upload.js](../src/server/upload.js)

<a id="live-error-unauthenticated"></a>
### `UNAUTHENTICATED`

- Cause: A guard (`{ authenticated: true }` or a guard that throws a plain error) rejects a connection without an authenticated identity, a document or smooth topic subscribe is denied as unauthenticated, or `maskNotFound` masks an unknown path.
- Consequence: The call or subscribe is refused before application code. The caller receives an UNAUTHENTICATED RpcError or LiveError, and streams enter their error state.
- Automatic recovery: None. Calls are not retried after sign-in.
- Next action: Sign the user in and reconnect so the connection carries an identity with `id`, `user_id` or `userId`. Check the guard and the auth wiring in the upgrade hook.
- Message patterns: <code>Access denied</code>; <code>Authentication required</code>; <code>document topic subscribe denied: &lt;denial&gt;</code>; <code>reauth failed</code>; <code>smooth topic subscribe denied: &lt;denial&gt;</code>
- Owning sources: [src/server.js](../src/server.js), [src/server/crdt.js](../src/server/crdt.js), [src/server/dispatch.js](../src/server/dispatch.js), [src/server/smooth.js](../src/server/smooth.js), [src/server/upload.js](../src/server/upload.js)

<a id="live-error-unavailable"></a>
### `UNAVAILABLE`

- Cause: The server is draining for graceful shutdown, so it rejects new RPC, binary, upload and server-side direct calls.
- Consequence: The new call gets an error reply (RpcError on the client), or a server-side direct call throws a LiveError unless a `fallback` is configured. Work already in flight continues.
- Automatic recovery: None for the rejected call. The client reconnects in the normal way once the draining server closes the socket.
- Next action: Retry after reconnecting to a healthy instance. Pass a `fallback` for direct calls so pages render degraded during deploys.
- Message patterns: <code>Server is shutting down</code>
- Owning sources: [src/server/dispatch.js](../src/server/dispatch.js), [src/server/upload.js](../src/server/upload.js)

<a id="live-error-unknown"></a>
### `UNKNOWN`

- Cause: An RPC, batch, stream or upload error reply arrives with no `code` field, for example from an incompatible server or a custom handler that writes raw replies.
- Consequence: The pending call rejects with an UNKNOWN RpcError using the reply's `error` text, or the message `Unknown error` or `Upload failed`. Only the reply's `params` and `details` are carried onto the error; other reply fields are not.
- Automatic recovery: None.
- Next action: Inspect the raw reply frame in the browser network panel and check the server version. Make sure every error reply includes a code, by throwing a LiveError in handlers.
- Message patterns: <code>Unknown error</code>; <code>Upload failed</code>
- Owning sources: [src/client/connection.js](../src/client/connection.js), [src/client/upload.js](../src/client/upload.js), [src/testing.js](../src/testing.js)

<a id="live-error-validation"></a>
### `VALIDATION`

- Cause: Arguments fail a `live.validated` or stream-args schema, or a server API is misused: invalid `live.push` or `live.notify` targets or options, alarm, tenant, `ctx.publish` jitter, `ctx.compensate` or `live.breaker` configuration.
- Consequence: A VALIDATION LiveError is thrown. Inside a handler it reaches the client as an RpcError with the message and, for schema failures, `issues`. At registration it fails at load time.
- Automatic recovery: None.
- Next action: For schema failures, fix the input using `issues`. For other messages, correct the server code or configuration the message names and redeploy.
- Message patterns: <code>[svelte-realtime] &lt;caller&gt;: target must name exactly one of userId / sessionId / topic</code>; <code>[svelte-realtime] &lt;caller&gt;: target.&lt;key&gt; must be a non-empty string</code>; <code>[svelte-realtime] &lt;caller&gt;: unsupported target keys: &lt;value&gt;</code>; <code>[svelte-realtime] alarm tenant metadata must match its wire topic</code>; <code>[svelte-realtime] ctx.publish jitterMs must be a finite number of milliseconds in [0, 60000]</code>; <code>[svelte-realtime] ctx.setAlarm / ctx.getAlarm / ctx.deleteAlarm require a live.stream (or live.room) declared with an { alarm: { onAlarm } } config.</code>; <code>[svelte-realtime] ctx.setAlarm(at): at must be a finite epoch-ms number</code>; <code>[svelte-realtime] live.notify: event must be a non-empty string</code>; <code>[svelte-realtime] live.notify: target must be an object like { userId }</code>; <code>[svelte-realtime] live.push({ topic }): requires a captured platform with requestTopic (svelte-adapter-uws &gt;= 0.6.0-next.39). - Owning sources: [src/server.js](../src/server.js), [src/server/alarm.js](../src/server/alarm.js), [src/server/breaker.js](../src/server/breaker.js), [src/server/ctx.js](../src/server/ctx.js), [src/server/dispatch.js](../src/server/dispatch.js), [src/server/history-compensation.js](../src/server/history-compensation.js), [src/server/push.js](../src/server/push.js), [src/server/room.js](../src/server/room.js), [src/server/tenant.js](../src/server/tenant.js)

<a id="operational-events"></a>
## Operational events

Structured events emitted through `emitOperationalEvent()` go to the sink installed with `setOperationalEventSink()` and, without a sink, to the console. Events marked console only are printed directly and never reach the sink. Every console copy is one line in this format, so the event name is searchable in plain logs:

`[lantean/diagnostic source=svelte-realtime component=<component> event=<event> severity=<severity>] <message>`

<a id="diagnostic-alarm.execution.failed"></a>
### `alarm.execution.failed`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>An alarm handler failed; the scheduler remains active.</code>
- Cause: A room's `onAlarm` handler throws or rejects, or the alarm fires with no platform captured. The event is logged after `onError` observers run.
- Consequence: That alarm's work did not finish, and anything it would have published is missing. With a durable store the execution is kept and marked failed. An in-memory alarm is used up.
- Automatic recovery: None for this alarm. It is not retried, and a durable failed execution waits for an explicit `requeue`. Other alarms and the scheduler keep running.
- Next action: Fix the handler error shown by your `onError` observer. For durable alarms, check the execution with `getExecution` or `executions`, then call `requeue` with a new `at`, or `complete` to discard it. Make retried effects idempotent with `ctx.alarm.idempotencyKey`.
- Owning sources: [src/server/alarm.js](../src/server/alarm.js)

<a id="diagnostic-alarm.execution.retained"></a>
### `alarm.execution.retained`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>An alarm execution outcome could not be confirmed; inspect retained executions before retrying.</code>
- Cause: After a durable alarm ran, the store's `complete` or `fail` call rejected, so the outcome was not recorded.
- Consequence: The record may still show as claimed, or a completion may have committed without being acknowledged. The handler may or may not have finished; the `outcome` attribute says whether it succeeded.
- Automatic recovery: None. The callback never runs again on its own, and abandoned claims do not expire.
- Next action: Fix the store problem. Look up the execution with `getExecution` and check the application side effects. Then call `complete` to discard it, or `requeue` with `allowAbandoned: true` once you have confirmed its worker stopped.
- Owning sources: [src/server/alarm.js](../src/server/alarm.js)

<a id="diagnostic-alarm.recovery.unresolved"></a>
### `alarm.recovery.unresolved`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>A durable alarm could not be resolved by this release and was retained.</code>
- Cause: The recovery poll finds a due durable alarm whose stored id or path matches no registered `onAlarm` handler in this release, or whose id matches more than one handler.
- Consequence: The alarm does not run. Its row is kept in the store unclaimed, so no data is lost, but the scheduled work is delayed until a compatible release handles it.
- Automatic recovery: Each later poll skips the row again. It runs automatically once a release that resolves it handles the poll. The event is logged once per id or path.
- Next action: Restore or rename the stream that declares this alarm id, remove the duplicate id, or roll back to a compatible release. Check the `alarmId`, `path` and `reason` attributes.
- Owning sources: [src/server/alarm.js](../src/server/alarm.js)

<a id="diagnostic-breaker.open"></a>
### `breaker.open`

- Severity: warn
- Delivered to: operational event sink
- Message patterns: <code>A circuit breaker refused an operation.</code>
- Cause: A `live.breaker` wrapper finds its breaker open: `guard()` throws `CircuitBrokenError`, or `isOpen()` returns true. This is logged once per open period.
- Consequence: The wrapped operation is not run. The caller gets the configured `fallback`, or a SERVICE_UNAVAILABLE error when no fallback is set.
- Automatic recovery: The breaker library decides when to let calls through again. The first call that passes resets the report, so the next open period is logged again.
- Next action: Investigate the failing dependency behind the breaker named in the `name` attribute. Check that the fallback is acceptable for users while the breaker stays open.
- Owning sources: [src/server/breaker.js](../src/server/breaker.js)

<a id="diagnostic-cron.execution.failed"></a>
### `cron.execution.failed`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>A cron handler failed; the scheduler remains active.</code>
- Cause: A cron handler throws or rejects during a matching tick, or publishing its return value fails.
- Consequence: That tick's run is lost and its result is not published. The cron error metrics increase.
- Automatic recovery: None for the failed tick, which is not retried. The job runs again at its next matching slot, and other jobs are not affected.
- Next action: Fix the handler error recorded under `path` and `error`. If a missed run matters, make the job catch up on its next run or trigger the work manually.
- Owning sources: [src/server/cron-engine.js](../src/server/cron-engine.js)

<a id="diagnostic-delivery-authorization.replaced"></a>
### `delivery-authorization.replaced`

- Severity: warn
- Delivered to: console only (bypasses the operational event sink)
- Message patterns: <code>A newer realtime() delivery policy replaced the active one; the replaced one stays retired.</code>
- Cause: The hooks of a second `realtime()` call, with a different `authorizeDelivery` function or options, run on a worker that already has an active delivery policy.
- Consequence: The newer policy decides every frame from then on. The replaced policy is retired for good, and its hooks are refused from then on.
- Automatic recovery: The takeover happens on its own and needs no reinstall. This is expected after a dev reload of `hooks.ws`.
- Next action: In production, make sure only one `realtime()` call with `authorizeDelivery` has its hooks mounted per worker. In development after a hook reload, no action is needed.
- Owning sources: [src/server/delivery-authorization.js](../src/server/delivery-authorization.js)

<a id="diagnostic-delivery-authorization.stale"></a>
### `delivery-authorization.stale`

- Severity: error
- Delivered to: console only (bypasses the operational event sink)
- Message patterns: <code>Hooks of a replaced delivery policy ran; their connections are closed.</code>
- Cause: A hook from a `realtime()` call whose delivery policy a newer policy has retired runs again. This is logged once per platform.
- Consequence: Each connection reaching such a hook is closed with code 1011 and is not served. For a retired call, `init` throws.
- Automatic recovery: None for the retired call, which never takes back over. Clients served by the active policy are not affected, and closed clients can reconnect.
- Next action: Remove the stale `realtime()` hooks so that only the active call's hooks are exported, or restart the server.
- Owning sources: [src/server/delivery-authorization.js](../src/server/delivery-authorization.js)

<a id="diagnostic-delivery-authorization.unavailable"></a>
### `delivery-authorization.unavailable`

- Severity: error
- Delivered to: console only (bypasses the operational event sink)
- Message patterns: <code>A delivery policy is configured but could not be installed; connections are closed.</code>
- Cause: A hook tries to install the configured `authorizeDelivery` policy and fails, typically because the adapter has no `platform.authorizeDelivery` or because `deliveryAuthorizationOptions` differ from the installed ones. This is logged once per platform.
- Consequence: The connection is closed with code 1011 before realtime serves it. No unchecked frames are delivered.
- Automatic recovery: Every later hook tries the install again, but a lasting cause keeps closing connections.
- Next action: Upgrade svelte-adapter-uws to a release that provides `platform.authorizeDelivery`, or remove `authorizeDelivery`. If the options changed, restart the server. Check the `error` attribute.
- Owning sources: [src/server/delivery-authorization.js](../src/server/delivery-authorization.js)

<a id="diagnostic-delivery-authorization.unguarded"></a>
### `delivery-authorization.unguarded`

- Severity: error
- Delivered to: console only (bypasses the operational event sink)
- Message patterns: <code>A connection reached realtime before its delivery policy was installed; export init or open from realtime().</code>
- Cause: Neither `init` nor `open` from the `realtime()` call ran first, so a `message`, `unsubscribe` or `close` hook installed the delivery policy. This is logged once per platform.
- Consequence: That connection was open before any policy existed and may already have received unchecked frames. It is still served, and every frame after the install is checked.
- Automatic recovery: The policy stays installed and is applied to all later frames. Frames sent before the install are not checked afterwards.
- Next action: Export `init` (or at least `open`) from the same `realtime()` call that configures `authorizeDelivery`.
- Owning sources: [src/server/delivery-authorization.js](../src/server/delivery-authorization.js)

<a id="diagnostic-direct-call.fallback.used"></a>
### `direct-call.fallback.used`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>A direct live-function call failed and returned its configured fallback.</code>
- Cause: A server-side direct call to a live function, such as a `.load()` from SSR, throws during the guard, validation, loader or filter, and the call was given a `fallback` option.
- Consequence: The caller gets the configured fallback instead of real data, so the rendered page shows placeholder content for that stream. The original error is not rethrown.
- Automatic recovery: None for this call. The next direct call runs the function again from the start.
- Next action: Fix the error reported in the `error` attribute for `path`. Make sure the fallback value renders sensibly. Use `onError` if you need the raw error.
- Owning sources: [src/server/dispatch.js](../src/server/dispatch.js)

<a id="diagnostic-forget.incomplete"></a>
### `forget.incomplete`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>Erasure could not be confirmed for every configured surface; resolve the failed cleanup and retry.</code>
- Cause: `live.forget` attempted every erasure surface and at least one in-memory surface, named document or the durable store failed. The surfaces are listed in `failedSurfaces`.
- Consequence: The user's data may still exist on the listed surfaces. The call rejects with FORGET_INCOMPLETE, or FORGET_STORE_FAILED when the durable store failed. `onForget` does not run.
- Automatic recovery: None. The erasure is not retried automatically, although owner changes the store already committed are still announced.
- Next action: Fix the failing surface: a missing dead-letter `purgeUser`, a missing aggregate reset policy, or a store outage. Then call `live.forget` again with the same user and tenant.
- Owning sources: [src/server/forget.js](../src/server/forget.js)

<a id="diagnostic-forget.owner-succession-unannounced"></a>
### `forget.owner-succession-unannounced`

- Severity: warn
- Delivered to: operational event sink
- Message patterns: <code>The erasure store reported room owner changes but no platform is available to publish them; configure configureForget({ platform }) or initialize the server before erasing.</code>
- Cause: The erasure store reports room owner changes caused by the erasure, but there is no erasure platform and no captured server platform to publish them through.
- Consequence: The owner changes are committed in the store, but subscribers on the rooms' owner topics are not told about the new owner and may keep showing the erased owner. The erasure itself is not affected.
- Automatic recovery: None. Running the erasure again does not re-announce these changes, because the store already committed them.
- Next action: Configure `configureForget({ platform })`, or initialize the server before running erasures, for example on a separate erasure runner. Have affected clients reload the rooms; the `count` attribute says how many changes went unannounced.
- Owning sources: [src/server/forget.js](../src/server/forget.js)

<a id="diagnostic-invariant.violated"></a>
### `invariant.violated`

- Severity: fatal, warn
- Delivered to: console only (bypasses the operational event sink)
- Message patterns: computed (search the event name).
- Cause: An internal runtime consistency check fails. Severity warn marks a recoverable violation; fatal marks state that could deliver messages to the wrong place. The message is the category name.
- Consequence: Warn: the violation is counted and processing continues. Fatal: on the server the worker exits with code 78 once the current callback finishes, and its connections drop.
- Automatic recovery: Warn: none needed, processing continues. Fatal: none within the process; recovery depends on the process supervisor restarting the worker.
- Next action: Restart a worker that exited with code 78. Record the category, its context and the `svelte_realtime_assertion_violations_total` metric, and report them to the maintainers with the versions you run.
- Owning sources: [src/shared/assert.js](../src/shared/assert.js)

<a id="diagnostic-operational.sink.failed"></a>
### `operational.sink.failed`

- Severity: error
- Message patterns: <code>The configured operational event sink failed; console fallback was restored for this event.</code>
- Cause: The sink installed with `setOperationalEventSink` throws or rejects while handling an operational event.
- Consequence: The original event is written to the console instead, so it is not lost, but it does not reach your logger or collector.
- Automatic recovery: The sink stays installed, and every later event is sent to it again. Console fallback applies only to events that fail.
- Next action: Fix the sink so it never throws or rejects. Check the `originalSource` and `originalEvent` attributes to find the events your collector missed.

<a id="diagnostic-poll.tick.failed"></a>
### `poll.tick.failed`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>A live.poll callback rejected; the interval remains active.</code>; <code>A live.poll callback threw; the interval remains active.</code>
- Cause: A `live.poll` callback throws, or the promise it returns rejects, on one interval tick.
- Consequence: The work of that tick is lost and anything it would have published is missing for that interval.
- Automatic recovery: The interval stays active and calls the callback again at the next tick.

<a id="diagnostic-reactive.derived.failed"></a>
### `reactive.derived.failed`

- Severity: error
- Delivered to: operational event sink
- Message patterns: <code>A derived stream recomputation failed; later source events may retry it.</code>
- Cause: Recomputing a `live.derived` stream throws after a source event, in its compute function, its middleware or while publishing the result.
- Consequence: No new value is published for the `topic`. Subscribers keep the last value they received, which may now be out of date.
- Automatic recovery: If another source event arrived during the failed run, it recomputes immediately. Otherwise the next source event triggers a recompute.
- Next action: Fix the compute error reported in the `error` attribute. Check that the source streams return data in the shape the derived function expects.

<a id="diagnostic-rpc.execution.failed-after-answer"></a>
### `rpc.execution.failed-after-answer`

- Severity: warn
- Delivered to: operational event sink
- Message patterns: <code>An RPC handler failed after a middleware had already answered the call.</code>
- Cause: A middleware answered an RPC before the handler chain finished (it returned an envelope or threw without waiting for `next()`), and the chain failed later.
- Consequence: The client already has the middleware's answer and never sees this failure. Work the handler did before failing may be partly applied. The `onError` option is not called for this failure.
- Automatic recovery: None. Shutdown drain tracks the still-running chain until it settles; the failure is reported only through this event.

- Severity: warn
- Delivered to: operational event sink
- Message patterns: <code>A middleware called next() after the call was answered; the rest of the chain did not run.</code>
- Cause: A middleware calls `next()` after the RPC already has an answer, for example from a timer or after returning its own envelope.
- Consequence: The rest of the chain does not run: inner middleware, guard and handler are skipped for that late call, and that `next()` returns a rejected promise. The client keeps the answer it already got.

- Severity: warn
- Delivered to: console only (bypasses the operational event sink)
- Message patterns: <code>An RPC response was not delivered.</code>
- Cause: Sending an RPC response hits backpressure, or the send throws because the socket closed mid-call. Emitted only in development.
- Consequence: On backpressure the response is buffered and may arrive late. If the socket closed, the client does not get it and its call rejects on disconnect or timeout. Delivery metrics record the outcome.

- Cause: A fire-and-forget call (no id, from `fireAndForget`) reaches a handler not wrapped in `live.volatile()`. Emitted only in development, once per path, for a bounded number of paths.

<a id="diagnostic-shutdown.drain.timed-out"></a>
### `shutdown.drain.timed-out`

- Severity: warn
- Delivered to: operational event sink
- Message patterns: <code>Shutdown drain budget expired with tracked handlers still active.</code>; <code>Shutdown tracked handlers drained before teardown.</code>
- Cause: During graceful shutdown, tracked in-flight work (RPCs and other tracked handlers) is still running when the drain budget ends: the largest `onShutdown` `drainMs`, default 5000 ms.
- Consequence: Teardown goes ahead with work still running; `remaining` gives the count. Those calls may be cut off and their responses lost. New calls have already been refused with UNAVAILABLE.
- Automatic recovery: None. `onShutdown` handlers still run and receive the drain outcome; the adapter `SHUTDOWN_TIMEOUT` is the hard cap.
- Next action: Find long-running handlers, or raise `drainMs` while keeping it below the adapter shutdown timeout. Make interrupted work safe to retry, for example with `live.idempotent`.
