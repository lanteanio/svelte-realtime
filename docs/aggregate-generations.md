# Aggregate reset generations

`live.aggregate(..., { forget: 'reset' })` changes its keyed noise generation when `live.forget` resets its reducer state. This applies to single-state, lifetime, tumbling and sliding aggregates. The default generation is worker-local: there is no storage dependency, but a process restart loses that generation and separate workers can have different reset histories.

For shared, persistent generations, configure `realtime({ aggregateGenerationStore: store })` with an `AggregateGenerationStore`. Configure it before the first aggregate load, source fold, snapshot settlement or timer publication. Normal imports may register aggregates before `realtime` is called; configuration fences and restarts those initial snapshot reads. Changing the store after use is refused. Each worker uses the same namespace, durable backing state, `privacySecret` and aggregate configuration.

## Erasure identity and ordering

The store exposes `namespace`, `issueErasure()`, `readGeneration(topic)` and `advanceGeneration(topic, erasure)`. A token is `{ namespace, sequence }`: the namespace contains 1-128 ASCII letters, digits, underscores or hyphens; sequence is a canonical decimal unsigned 128-bit integer, without a sign or leading zeroes. Sequence `"0"` is the initial generation and is never an issued erasure identity. The namespace and sequence contain no user identifier, hash or other personal data.

The application calls `store.issueErasure()` once per logical erasure, durably retains the returned token with its erasure request, and passes it as `live.forget(userId, { tenantId, aggregateErasure })` on every worker and retry. It must retain that token before starting any erasure. A lost allocation reply can leave a gap; an unacknowledged token is not used. Never derive the token from a user ID, clock, local counter, request attempt or worker ID. The option is required when a store is configured, even if that worker currently has no reset aggregate. Supplying it without a configured store is refused.

`issueErasure()` durably increments one store-wide sequence and never reuses a value. `advanceGeneration(topic, token)` validates that the token belongs to this namespace and was issued, atomically persists `max(current, token.sequence)`, and returns the committed current token. Concurrent calls must be linearizable. Equal and older tokens do not increment again or move the generation backwards. A retry of an old erasure can observe a newer current generation; its erasure identity remains the same. Numeric comparison uses the integer sequence, not decimal-string lexicographic order.

The generation scope is the registered aggregate's topic, or the base topic shared by all of its windows. It is independent of the erased user's tenant: aggregates retain their existing global/topic-qualified scope and a reset discards the whole aggregate. Applications needing independent tenant aggregates use distinct registered topics. `tenantId` continues to scope the other erasure surfaces; it is never used as the erasure identity.

## Bootstrap and publication

Every newly registered reset aggregate reads its durable generation before invoking its snapshots, serving a load or publishing. A pending read or reset quarantines that aggregate: source events still reach their ordinary subscribers but are not folded into the aggregate, and no aggregate output is emitted. Start ingestion after aggregate loaders have completed, and pause ingestion around erasure when every contribution must be retained. There is no unbounded event queue. Snapshots must read already-erased durable application data; this store retains generation metadata, not reducer snapshots.

At erasure, old reducer, cohort and held-output references are discarded and pending debounced output is canceled before awaiting storage. Old snapshots and pending loads are invalidated. Once the advance is committed, clean initial state is published so subscribers discard their old held value, and source folding resumes. Every subsequent noisy output includes the namespace and generation in its HMAC seed alongside the topic and window boundary. The initial clean reset remains an unperturbed initial value, including below the contributor threshold.

The UTF-8 HMAC seed starts with `tenantId + '\0' + outputTopic + '\0' + windowStart`; the reserved tenant slot is currently empty. With a store it always appends `'\0store\0' + namespace + '\0' + sequence`, including sequence `"0"` at initial bootstrap. Without a store, the initial seed has no suffix; after a reset it appends `'\0local\0' + sequence`. These separate domains prevent any durable namespace from colliding with a worker-local generation. Window boundaries retain their existing meaning and never serve as erasure identities.

An RPC or SSR load invalidated after computation is refused with `UNAVAILABLE` before its result is delivered; the caller can retry after reset completes. SSR loads honor their configured fallback. Reducer, contributor, initializer, window and snapshot callbacks cannot restore or publish state from an older reset generation.

An aggregate keeps one in-flight store operation and its highest requested token. Overlapping requests coalesce; no per-erasure history accumulates in the worker. A completed equal or older token does not clear later contributions. Store failure, malformed results, a backwards result, initialization failure or publication failure leaves the aggregate closed until the same token (or a newer one) is retried successfully. `configureForget({ timeoutMs })` also bounds each store advance; a late response cannot reopen or publish from the failed attempt. While a timed-out raw store call remains pending, retries fail immediately rather than accumulate waiters; once it settles, a retry can advance again. Other independent erasure surfaces continue, and the caller receives `FORGET_INCOMPLETE`. Bootstrap failures reject loads and require a fresh registration to retry the read. Store exception payloads are not logged or returned through the erasure result.

The application must fan out the same erasure token to every active worker and await their results. The store does not notify workers, revoke a worker that has not received the erasure, or synchronize source delivery. A worker joining after the committed advance restores the current generation before publishing. Restoring a failed module reload also creates a fresh registration and reads the generation before snapshots or output. Fence ingestion and worker admission during the erasure if an application requires a cluster-wide publication barrier.

## Durable storage requirements

Persist the namespace, issuance counter and one high-water mark per aggregate topic. This is constant state per topic, independent of the number of erasures. The counter and topic updates survive acknowledged writes, restarts, failover and backup restoration. Namespace changes are deliberate migrations: never restore an older counter/high-water mark under a namespace that has already been used. Retain topic high-water marks even while an aggregate is unregistered; deleting one would allow a later registration to reuse old noise. A fixed topic-capacity limit must refuse a new topic rather than evict an existing mark. Counter exhaustion at `340282366920938463463374607431768211455` refuses new identities rather than wrapping. Invalid or unissued tokens must not change stored state.

Durable implementations must prove atomic max under concurrent writers, stable duplicate/older results, namespace validation, unissued-token refusal, crash-safe issuance and updates, restart bootstrap, and explicit capacity/exhaustion refusal. The runtime's consumer checks are in `test/aggregate-generation.test.js`; the public `AggregateGenerationStore` and `AggregateErasureToken` declarations are in `svelte-realtime/server`. The store contract is additive in the 0.6 API and requires no client wire change.

Reset generations prevent reuse across erasures; they do not provide differential privacy. Noise remains constant within a window and generation, contributions are not clipped, and releases have no composition accountant. A known true value can reveal the offset for the corresponding generation and window.
